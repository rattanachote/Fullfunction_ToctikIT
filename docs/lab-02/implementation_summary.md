## ส่วนที่ 1: ขั้นตอนการเตรียมระบบและการจัดทำเอกสาร (Spec DD)

1.  **คัดลอกระบบรากฐานจาก Lab 1**
    *   คัดลอกไฟล์โปรเจกต์ `client` และ `server` รวมถึง `.gitignore` และ `README.md` จากโฟลเดอร์ `lab1` มาเป็นฐานข้อมูลตั้งต้น
    *   รัน `npm install` ในฝั่ง Client และ Server เพื่อติดตั้ง dependencies ทั้งหมด
    *   ติดตั้งตัวจัดการอัปโหลดไฟล์ `multer` และ `@types/multer` เพิ่มเติมบนฝั่ง Server
2.  **เขียนเอกสารข้อกำหนดและการวางแผน (Spec-Driven Development)**
    *   สร้างโฟลเดอร์สำหรับเก็บเอกสารที่ `docs/lab-02/`
    *   จัดทำไฟล์เอกสารรวม 6 ไฟล์เพื่อใช้อ้างอิงและส่งงาน:
        *   **`specification.md`**: ขอบเขตงาน (Inclusions/Exclusions), ข้อกำหนดฟังก์ชัน (FR), และกฎธุรกิจ (BR) เช่น ขนาดไฟล์ ขนาดตัวอักษร และสิทธิ์การใช้งาน
        *   **`api-spec.md`**: โครงสร้าง REST API endpoints ข้อมูลที่ต้องส่ง (Payloads), query parameters สำหรับคัดกรองตั๋ว, และ HTTP Status Codes
        *   **`ui-spec.md`**: รายละเอียดชุดสีธีม Zen Green และรูปแบบฟังก์ชันหน้าจอทั้ง 4 หน้าจอ
        *   **`tests.md`**: แผนการทดสอบทางซอฟต์แวร์และการเชื่อมโยง (Traceability)
        *   **`reviewer.md`**: ตารางบันทึกการทำ Peer Review การทำ Pull Requests ต่างๆ
        *   **`ai-use.md`**: บันทึกการส่ง Prompt เพื่อช่วยเขียนโค้ดและสะท้อนผลการใช้เครื่องมือ AI

## ส่วนที่ 2: การออกแบบฐานข้อมูล (Database Layer)

1.  **แก้ไขโครงสร้างฐานข้อมูล (`server/prisma/schema.prisma`)**
    *   ปรับการตั้งค่าไปใช้ **SQLite (`dev.db`)** ชั่วคราวสำหรับการพัฒนาในเครื่อง (เนื่องจากตัวติดตั้ง PostgreSQL ของ Windows ติดเงื่อนไขสิทธิ์การเข้าถึงแบบเงียบ)
    *   ออกแบบ Model ฐานข้อมูลใหม่:
        *   `RequesterUser` (ผู้ใช้งานจำลอง) - เก็บ ID, ชื่อ, อีเมล และสถานะการใช้งาน
        *   `Category` (หมวดหมู่ตั๋ว) - ความสัมพันธ์แบบ 1-to-Many กับตั๋ว
        *   `RelatedSystem` (ระบบไอทีที่เกี่ยวข้อง) - เก็บรายการเครื่อง/ซอฟต์แวร์ที่แจ้งปัญหา
        *   `Ticket` - เก็บหมายเลขตั๋วอย่างเป็นทางการ, รายละเอียดเนื้อหา, ลำดับความสำคัญ, สถานะ และความสัมพันธ์
        *   `Attachment` - เก็บชื่อไฟล์จริง, ชื่อระบบสุ่มป้องกันการซ้ำ, ขนาด, ประเภท, และสถานะการลบข้อมูล (Soft-removal)
2.  **รันคำสั่ง Migration และ Seeding ข้อมูลตั้งต้น**
    *   เขียนโค้ดสำหรับเตรียมข้อมูลทดสอบใน `server/prisma/seed.ts` ให้เป็นแบบ Idempotent (ทำงานซ้ำได้ข้อมูลไม่ซ้ำ)
    *   รันคำสั่ง `npx prisma migrate dev --name init` เพื่อสร้างไฟล์ฐานข้อมูล `dev.db` และโหลดข้อมูลจำลองเข้าสู่ตารางโดยอัตโนมัติ

## ส่วนที่ 3: การพัฒนา API หลังบ้าน (Express Backend REST API)

พัฒนา API ทั้งหมดที่โฟลเดอร์ `server/src/app.ts` โดยมีรายละเอียดการคำนวณและประมวลผลที่สำคัญดังนี้:

1.  **ตัวกลางตรวจสอบตัวตนจำลอง (requireRequester Middleware):**
    *   ดึงค่า `X-Requester-Id` จาก headers เพื่อเช็คว่ามีผู้ส่งคำขอเข้ามาหรือไม่ และแปลงข้อมูลเป็นตัวเลขก่อนส่งต่อไปยัง Endpoint ต่างๆ
2.  **การดึงข้อมูลพื้นฐาน (GET /api/requesters, /api/categories, /api/systems):**
    *   ดึงเฉพาะผู้ใช้และระบบที่มีสถานะเป็น `isActive: true`
3.  **การแจ้งสร้างตั๋ว (POST /api/tickets):**
    *   ตรวจสอบข้อมูลที่ป้อนเข้ามาตามขอบเขต (เช่น Summary ไม่เกิน 100 อักษร, Description ไม่เกิน 2000 อักษร)
    *   คำนวณหาเลขตั๋วอัตโนมัติ: นับจำนวนตั๋วของปีปัจจุบัน แล้วนำค่าที่ได้มาบวก 1 และแสดงผลเป็นรูปแบบ `TKT-YYYY-XXXXXX` (เช่น `TKT-2026-000001`)
4.  **การดึงรายการตั๋วและแบ่งหน้า (GET /api/tickets):**
    *   ตรวจสอบสิทธิ์: คัดแยกให้เห็นเฉพาะตั๋วที่ผู้ใช้คนปัจจุบัน (`requesterId`) เป็นผู้สร้างเท่านั้น
    *   รองรับคำค้นหา (`search` contains), กรองข้อมูลตาม Categories, Priorities, Statuses, ทำการเรียงลำดับ (Sorting) และแบ่งสัดส่วนข้อมูลตามหน้า (Pagination)
5.  **การอัปโหลดไฟล์แนบตั๋ว (POST /api/tickets/:id/attachments):**
    *   ใช้ตัวกรอง `multer` ตรวจขนาดไฟล์ห้ามเกิน 5MB และนามสกุลต้องเป็น JPG, JPEG, PNG, WEBP หรือ PDF เท่านั้น
    *   ตรวจเช็คจำนวนไฟล์แนบที่ยังมีผลใช้งานอยู่ (isRemoved = false) หากมีครบ 5 ไฟล์แล้วระบบจะปฏิเสธการอัปโหลดเพิ่ม
6.  **การดาวน์โหลดและการลบไฟล์แนบแบบ Soft-removal (GET / DELETE):**
    *   **ดาวน์โหลด:** ตรวจความเป็นเจ้าของตั๋วก่อนดาวน์โหลด และบล็อกไฟล์ที่ถูกลบไปแล้ว
    *   **Soft-removal:** อัปเดตสถานะในตาราง `Attachment` ให้เป็น `isRemoved = true` และบันทึกเหตุผลที่ขออัปเดต โดยจะลบไฟล์ต้นฉบับออกจากโฟลเดอร์เก็บข้อมูลจริงๆ (Disk Storage) เพื่อความปลอดภัยทางข้อมูล

## ส่วนที่ 4: การพัฒนาหน้าจอส่วนหน้า (React Client UI)

ตกแต่งหน้าจอโดยอ้างอิงสีเขียว **Zen Green Theme** ใน `client/src/App.tsx` ทั้งหมด 4 หน้าจอหลัก:

1.  **หน้าจอจำลองล็อกอิน (Requester Selection):**
    *   ให้เลือกผู้ใช้งานจริงที่มีอยู่ในฐานข้อมูล และเก็บสถานะไว้ใน Session เพื่อรักษาสถานะไว้เมื่อรีเฟรชหน้าจอ
2.  **หน้าจอรายการตั๋วของฉัน (My Tickets):**
    *   แสดงตั๋วทั้งหมดในตาราง มีแถบค้นหา ตัวกรองแบบ dropdown และการแบ่งหน้า
    *   แสดงสถานะความสำคัญด้วย Badges สีสันต่างกัน (แดง ส้ม เขียว)
3.  **หน้าจอสร้างตั๋ว (Create Ticket):**
    *   ฟอร์มรับข้อมูลหมวดหมู่, ตัวระบบ, ลำดับความสำคัญ และรายละเอียด พร้อมทั้งแสดงแถบอัปโหลดไฟล์ และแสดงข้อความเตือนเมื่อไฟล์มีขนาด/ประเภทไม่ถูกต้อง
4.  **หน้าจอรายละเอียดและการจัดการตั๋ว (Ticket Detail):**
    *   ฝั่งซ้ายแสดงข้อมูลของตั๋วแบบอ่านอย่างเดียว (Read-only) เป็นการ์ดสีครีมงาช้าง
    *   ฝั่งขวาแสดงส่วนการจัดการไฟล์แนบ มีฟังก์ชันคลิกเพื่อดาวน์โหลดไฟล์เดิม, อัปโหลดไฟล์เพิ่มเข้ามาใหม่ (โดยระบบจะเช็คโควตาเดิมไม่ให้เกิน 5 ไฟล์), และมีปุ่มขอลบไฟล์แนบที่จะมีหน้าต่างป็อปอัพขึ้นมาให้พิมพ์เหตุผลเพื่อขอยืนยันการลบแบบ Soft-removal
