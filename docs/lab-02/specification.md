# Lab 2 Sprint Engineering Specification

## 1. Sprint Goal
Create a professional and responsive Requester-facing ticketing experience for the TokTickIT platform. The sprint delivers the UI foundation (Zen Green theme), ticket creation, attachments lifecycle management (including validation and soft-removal), ticket listings (with search, filtering, sorting, and pagination), and ticket details inspection, while ensuring requester-ownership privacy through a temporary Development Requester selection mechanism.

## 2. Stakeholder Request Interpretation
The IT department needs to receive support tickets from end-users. The application must allow a user to:
*   Choose a simulated identity (Development Requester) for testing.
*   Describe a problem with a summary and description.
*   Select the category and affected system.
*   Attach up to 5 files (validating type and size <= 5MB).
*   Submit the ticket and receive a unique, system-generated Ticket Number.
*   Browse, search, sort, filter, and paginate their own tickets.
*   Open any of their tickets to inspect details, add further attachments, or soft-remove active attachments.
*   Ensure one requester cannot access or modify another requester's tickets.

## 3. Scope

### Included
*   **Development Requester Selection:** A temporary dropdown selector to simulate logged-in requester sessions.
*   **Create Ticket Form:** Inputs for Category, Related System, Priority, Summary, Description, and Attachments.
*   **My Tickets List:** Pagination, sorting (by Date/Status/Priority), search (by Ticket No/Summary), and filters (by Category/Priority/Status).
*   **Ticket Detail View:** Read-only details screen for existing tickets, showing metadata, attachments, and options to add/remove files.
*   **Attachment Management:** Upload validations, downloading active attachments, and soft-removal (retaining metadata but blocking download/preview).
*   **Data Models & Seeding:** Prisma models and idempotent seed script.

### Excluded
*   Real authentication, password hashing, and user sessions (slated for Lab 3).
*   IT Staff dashboard, ticket claiming, reassigning, or updating IT Priority.
*   Public comments, internal notes, and event log tracking.
*   Ticket status transitions beyond the initial "New" state.
*   Admin management screens.

## 4. Functional Requirements
*   **FR-01 (Requester Selector):** The system must display a selection screen listing active Development Requesters before entering the app.
*   **FR-02 (Application Shell):** The main navigation header must display the current requester's name and provide a "Change Requester" action.
*   **FR-03 (Create Ticket):** Requesters can submit a form to create a new ticket.
*   **FR-04 (Ticket No Generation):** The backend must generate a unique ticket number formatted as `TKT-YYYY-XXXXXX` (where YYYY is current year and XXXXXX is an incremental sequence).
*   **FR-05 (Attachment Upload):** Requesters can upload files of types JPG, JPEG, PNG, WEBP, and PDF, with a size limit of 5MB per file, up to 5 active attachments per ticket.
*   **FR-06 (Ticket List):** Requesters can view a list of their own tickets.
*   **FR-07 (Search & Filter):** Requesters can search their tickets by keyword and filter by Category, Priority, and Status.
*   **FR-08 (Sorting & Pagination):** Requesters can sort by creation date, status, or priority, and page through results.
*   **FR-09 (Ticket Detail):** Requesters can view a read-only details screen of their owned tickets.
*   **FR-10 (Attachment Management):** Requesters can upload additional attachments or soft-remove existing attachments on their tickets.
*   **FR-11 (Access Control):** The system must block a requester from viewing or modifying tickets belonging to another requester.

## 5. Business Rules
*   **BR-01 (Ticket ID):** The official Ticket Number is generated by the backend and must be unique.
*   **BR-02 (Initial Status):** A new ticket begins with the status `New`.
*   **BR-03 (Testing Identity):** The selected Requester identity is for testing only and does not represent secure authentication.
*   **BR-04 (Attachment Validation):** Only JPG, JPEG, PNG, WEBP, and PDF files are allowed. Maximum file size is 5MB. A ticket cannot have more than 5 active (non-removed) attachments at any time.
*   **BR-05 (Soft-removal):** Removing an attachment must mark it as removed in the database and capture a removal reason. Removed files must not be downloadable or previewable.
*   **BR-06 (Ownership Enforce):** A requester can only view, download, or edit attachments on tickets where `requesterId` matches their current active ID.

## 6. UI Specification Summary
*   **Zen Green Theme Tokens:**
    *   Primary green: `#006B3C` (header, primary buttons, strong emphasis)
    *   Secondary green: `#0B7A46` (active tabs, links, hover states)
    *   Pale green: `#EAF6EF` (selected items, success alert)
    *   Page background: `#F5F7F6` (subtle near-white)
    *   Text: Dark charcoal-green (`#1C2E24`)
    *   Read-only fields: Warm ivory shading (`#FAF9F6`)
*   **Responsiveness:**
    *   Desktop (>= 992px): Multi-column layout, centered content.
    *   Tablet (768px-991px): Two-column layout where practical.
    *   Mobile (< 768px): Single column stacked layout.

## 7. Data Changes
*   **Prisma Schema Additions:**
    *   `RequesterUser` model mapping to active/inactive testers.
    *   `Ticket` model mapping to IT support tickets.
    *   `Attachment` model tracking files and soft-removal metadata.
    *   `RelatedSystem` model mapping to affected software/hardware systems.
    *   `Category` model (relationship updated).

## 8. API Contract
*   `GET /api/requesters` -> returns JSON array of active requesters.
*   `GET /api/categories` -> returns JSON array of categories.
*   `GET /api/systems` -> returns JSON array of active related systems.
*   `POST /api/tickets` -> creates a ticket, returns status 201 and created ticket object.
*   `GET /api/tickets` -> returns JSON object containing paginated tickets list and metadata.
*   `GET /api/tickets/:id` -> returns details of one ticket if owned.
*   `POST /api/tickets/:id/attachments` -> uploads an attachment for a ticket.
*   `GET /api/attachments/:id` -> downloads the attachment.
*   `DELETE /api/attachments/:id` -> soft-removes the attachment.

## 9. Acceptance Criteria
*   **AC-01 (Creation Success):** Given valid ticket input, when the requester submits the form, then a new ticket is saved and the generated ticket number is displayed.
*   **AC-02 (Identity Redirect):** Given no requester is selected, when a user attempts to view My Tickets, then the selector screen is displayed.
*   **AC-03 (Ownership Separation):** Given Requester B is active, when they attempt to query details for a ticket owned by Requester A, then the API returns 403 Forbidden.
*   **AC-04 (File Validation):** Given an attachment of size 6MB, when the user uploads it, then the system rejects the file and displays a validation error.
*   **AC-05 (Soft-removal Integrity):** Given a soft-removed attachment, when a user attempts to download it, then the API returns 404/403 and blocks retrieval.

## 10. Definition of Done
*   All required database models are created and seeded.
*   All API endpoints implemented and verified with tests.
*   All UI screens created and verified visually against style guide.
*   Automated Vitest tests (unit and component) and Playwright E2E tests pass.
*   Staged feature branches merged to `lab2-staging`, then release merged to `main`.
*   Documents and screenshots submitted according to instructions.

## 11. Assumptions and Decisions
*   **Database Engine:** For local development and testing, SQLite is used temporarily due to system privileges, but the code and Prisma schema are kept database-agnostic.
*   **File Storage:** Uploaded files are stored in the server's local directory (`server/uploads/`) using sanitized filenames.
